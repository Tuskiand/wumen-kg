## 1. 项目概述

- 项目名称：吴门医案知识图谱管理系统
- 文档版本：V1.1
- 修订日期：2026-05-13
- 建设目标：围绕《吴门医案》知识图谱的浏览、检索、维护、导入和分析，建设一套前后端分离的图谱管理系统，服务于中医医案研究、知识组织和后续智能分析。

## 2. 项目背景

《吴门医案》包含医家、病名、证型、病因、病机、病位、症状、脉象、舌象、治法、方剂、药物等多类知识。传统文本材料难以支持跨医案关联检索、路径分析和结构化管理，因此需要把文本抽取结果组织成图数据库，并提供统一的展示、查询、导入和治理能力。

#### 9.3.2 医家比较的数据准备规则

医家比较不是对全库直接硬算，而是先围绕“当前病名”给每位医家构造一个局部研究上下文。

| 步骤 | 当前实现 |
| --- | --- |
| 1 | 先锁定病名节点 `B病名`，例如“中风” |
| 2 | 找出与该病名有关的医家 `A医家` |
| 3 | 汇总该医家在该病名下涉及的 `source_cases` |
| 4 | 取该医家的病名局部快照，节点类型只保留 `A医家`、`B病名`、`C证型`、`D病因`、`E病机` |
| 5 | 后续所有节点比较、路径比较、子图比较都只在这个局部快照里做 |

这样做的目的很直接：

- 避免把无关病名的数据混进来
- 避免一个医家在别的病里的特征污染当前病名比较
- 保证每次比较都能解释成“某病名下不同医家的辨证差异”

#### 9.3.3 节点比较算法

节点比较解决的是一个简单问题：不同医家在“证型、病因、病机”三类特征上到底像不像。

**一、节点集合构造**

- 先从每位医家的局部快照里，只取与当前医家直接相连的 `C证型`、`D病因`、`E病机`
- 同名同类型节点按 `(type, name)` 规整成同一个“规范键”
- 如果同一个规范键对应多个节点 ID，保留字典序更小的 ID 作为代表
- 于是每位医家都会得到三组集合：
  - `patterns`
  - `causes`
  - `mechanisms`

**二、共同节点与独有节点**

- 共同节点：多个医家的规范键交集
- 独有节点：当前医家集合减去共同节点集合
- 页面里的“共同节点”“医家独特点画像”就是按这个规则出的

**三、相似度矩阵**

后端会在 Neo4j GDS 中构造“医家-特征”投影图，再跑 `nodeSimilarity`。

投影规则：

- 医家节点：`A医家`
- 特征节点：按当前页签类别选 `C证型`、`D病因`、`E病机`，或三类一起选
- 投影边：某医家在当前病名对应的 `source_cases` 内，与某特征节点存在直接关系

当前输出 3 种相似度：

| 指标 | 含义 | 公式 |
| --- | --- | --- |
| Jaccard | 看交集占并集比例 | `|A ∩ B| / |A ∪ B|` |
| Overlap | 看交集占较小集合比例 | `|A ∩ B| / min(|A|, |B|)` |
| Cosine | 看两位医家的特征向量方向是否接近 | `(v1 · v2) / (||v1|| * ||v2||)` |

页面支持按 4 个维度切矩阵：

- 总体 `overall`
- 证型 `patterns`
- 病因 `causes`
- 病机 `mechanisms`

**四、RWR 核心节点排序**

节点比较页除了相似度矩阵，还会给每位医家跑一遍 RWR。

当前实现参数如下：

| 参数 | 当前值 |
| --- | --- |
| 锚点 | 当前医家节点 + 当前病名节点 |
| 初始个性化向量 | 医家 0.5，病名 0.5 |
| 主重启概率 | `0.25` |
| 备选重启概率 | `0.15`、`0.35` |
| 最大迭代次数 | `100` |
| 收敛阈值 | `1e-6` |
| 输出 TopK | `10` |

RWR 迭代公式可写成：

```text
next_score = r * personalization + (1 - r) * graph_propagation(score)
```

其中：

- `r` 是重启概率
- `personalization` 只在“当前医家、当前病名”两个锚点上有初值
- `graph_propagation` 表示把当前分数均匀分给邻居

实现细节：

- 图是无向图
- 节点类型只保留 `A医家`、`B病名`、`C证型`、`D病因`、`E病机`
- RWR 算完后，再按 `(type, name)` 做一次规范化聚合
- 最终页面展示的是 `C/D/E` 三类节点的 TopK 排名

这样做的意义：

- 比单纯按连接次数排序更稳
- 能把“离当前医家和当前病名都近”的节点顶上来
- 不容易被单个高连接枢纽节点带偏

#### 9.3.4 辨证路径比较算法

路径比较解决的问题是：医家不是只“用了哪些点”，而是“这些点之间怎么连成辨证链”。

**一、直接特征集合**

先从当前医家的局部快照里取出与医家直接相连的：

- `D病因`
- `E病机`
- `C证型`

**二、结构边集合**

再在局部快照里识别 3 类结构关系：

- `D病因 - E病机`
- `C证型 - E病机`
- `C证型 - D病因`

**三、路径拼接规则**

系统按下面顺序生成路径：

| 路径类型 | 生成条件 |
| --- | --- |
| `D-E-C` 完整链 | 医家同时直接关联病因、病机、证型，且存在 `D-E` 和 `C-E` 结构边 |
| `D-E` 部分链 | 存在病因和病机，且两者之间有结构边，但没进入完整链 |
| `E-C` 部分链 | 存在病机和证型，且两者之间有结构边，但没进入完整链 |
| `D-C` 部分链 | 病因和证型之间存在结构边 |
| `D` 单点 | 剩余未被使用的病因 |
| `E` 单点 | 剩余未被使用的病机 |
| `C` 单点 | 剩余未被使用的证型 |

例子：

```text
风邪外袭 -> 痰瘀阻络 -> 痰热内闭证
```

会被识别成一条 `D-E-C` 完整链。

**四、共享路径与独有路径**

- 每条路径会生成唯一签名 `signature`
- 两位医家只要签名一致，就视为共享路径
- 不在共享集合里的路径，就是该医家的独有路径

**五、完整度和差异度**

页面会给每位医家输出路径完整度：

```text
complete_ratio = 完整链数量 / 全部路径数量
```

还会给每对医家输出差异分：

```text
difference_score = 1 - |shared_paths| / |union_paths|
```

解释：

- 越接近 `0`，两位医家路径越像
- 越接近 `1`，两位医家路径越不一样

#### 9.3.5 核心子图比较算法

子图比较解决的问题是：把病名、医家、证型、病因、病机和它们之间的关系一起看，整体结构像不像。

**一、核心子图抽取规则**

核心子图不是把局部快照全拿过来，而是严格筛一遍。

当前纳入规则如下：

| 规则 | 说明 |
| --- | --- |
| 锚点 1 | 当前医家 `A医家` 必进 |
| 锚点 2 | 当前病名 `B病名` 必进 |
| 特征节点 | 只有同时被“当前医家”和“当前病名”指向的 `C/D/E` 节点，才允许进入核心子图 |
| 医家边 | 已纳入特征节点对应的“医家-特征”边保留 |
| 病名边 | 已纳入特征节点对应的“病名-特征”边保留 |
| 结构边 | 已纳入特征节点之间，若真实存在 `C-D`、`C-E`、`D-E` 结构边，则保留 |

这条规则很关键，因为它会主动排除“只被医家指到、但没有病名侧证据”的噪声点。

**二、共同节点与共同边**

- 共同节点：不同医家的核心子图里，规范键一致的 `C/D/E` 节点
- 共同边：比较时会把医家名统一规整成“当前医家”，再比较边签名

这样做的好处是：

- 不会因为医家姓名不同导致“同结构边”被判成不同
- 能更稳定地找出共性的辨证结构

**三、三层 Jaccard 指标**

页面当前对子图给 3 层 Jaccard：

| 指标 | 公式 | 含义 |
| --- | --- | --- |
| `node_jaccard` | `|节点交集| / |节点并集|` | 比节点组成是否相近 |
| `edge_jaccard` | `|边交集| / |边并集|` | 比结构边是否相近 |
| `subgraph_jaccard` | `|(节点+边)交集| / |(节点+边)并集|` | 把节点和边合起来看整体相似度 |

**四、关系节点化图表示**

为了做向量嵌入，系统会把核心子图转成“关系节点化”图：

```text
实体节点 -- 关系节点 -- 实体节点
```

也就是：

- 原来的一条关系，不直接作为边保存
- 而是先变成一个“关系节点”
- 再用两条边把源实体、关系节点、目标实体串起来

这样做是为了在图嵌入里保留“关系类型在结构中的位置”，而不是只保留无标签连接。

**五、三套向量嵌入**

当前系统对每位医家的核心子图生成 3 套图向量：

| 算法 | 侧重点 |
| --- | --- |
| NetLSD | 偏整体结构轮廓 |
| FGSD | 偏节点间结构距离分布 |
| Graph2Vec | 偏局部子结构模式 |

之后对任意两位医家的向量算余弦相似度：

```text
cosine(v1, v2) = (v1 · v2) / (||v1|| * ||v2||)
```

页面展示的就是：

- `netlsd_cosine`
- `fgsd_cosine`
- `graph2vec_cosine`

#### 9.3.7 算法选择结论

当前页面的算法路线可以概括成一句话：

- 节点层：GDS 节点相似度 + RWR
- 路径层：规则化辨证链抽取
- 子图层：核心子图筛选 + Jaccard + 图嵌入余弦相似度

这样分层的原因是：

- 节点层最适合回答“用了哪些证型、病因、病机”
- 路径层最适合回答“这些点怎么组成辨证逻辑”
- 子图层最适合回答“整体结构风格像不像”

## 10. 数据导入需求

### 10.1 当前导入方式

- 仅支持上传一个 CSV 文件
- 文件必须是三列表
- 表头必须严格为 `subject,relation,object`
- `subject` 和 `object` 的值必须为 `名称(类型)` 格式
- 需要填写 `source` 和 `source_case`
- 可选填写 `schema`

### 10.2 示例

```csv
subject,relation,object
薛雪(A医家),病名为,中风(B病名)
中风(B病名),证型为,风痰闭阻证(C证型)
风痰闭阻证(C证型),治法为,化痰开窍(J治法)
```

### 10.3 当前校验规则

| 校验项 | 说明 |
| --- | --- |
| 文件数量 | 只能上传 1 个文件 |
| 表头 | 必须严格匹配 `subject,relation,object` |
| 空值 | 任一行缺少 `subject`、`relation` 或 `object` 都直接报错 |
| 实体格式 | `subject`、`object` 必须写成 `名称(类型)` |
| 编码 | 支持 `utf-8-sig`、`utf-8`、`gbk` |
| schema 合法性 | 若填写 schema，schema 必须在系统定义内 |
| 实体类型合法性 | `schema=tcm` 时校验实体类型 |
| 关系类型合法性 | `schema=tcm` 时校验关系类型 |
| 关系方向合法性 | `schema=tcm` 时校验起点类型、关系类型、终点类型组合 |

### 10.4 当前标准化导入过程

1. 上传三列表 CSV
2. 后端解析 CSV
3. 基于 `source + source_case` 计算作用域
4. 生成标准化临时 CSV 到 `backend/neo4j_import`
5. 通过 Neo4j `LOAD CSV` 执行追加导入
6. 返回新增节点、重复节点、新增关系、重复关系统计

### 10.5 当前标准化临时 CSV 字段

| 字段 | 说明 |
| --- | --- |
| `relation_id` | 关系唯一标识 |
| `subject_id` | 起点节点 ID |
| `subject_name` | 起点节点名称 |
| `subject_type` | 起点节点类型 |
| `relation` | 关系类型 |
| `object_id` | 终点节点 ID |
| `object_name` | 终点节点名称 |
| `object_type` | 终点节点类型 |
| `source` | 来源卷册 |
| `source_case` | 来源医案 |

### 10.6 当前 ID 生成策略

- 节点 ID 不直接使用原始名称
- 系统对 `source + source_case + type + name` 做哈希，生成节点 ID
- 系统对 `source + source_case + subject_id + relation + object_id` 做哈希，生成关系 ID
- 同名同类型实体在不同来源或不同来源医案下会生成不同 ID，因此会并存，不会自动合并

### 10.7 当前导入语义

- 采用追加导入
- 不做跨医案同名实体自动合并
- 同一作用域内完全重复的节点和关系会按规则去重
- 导入后节点和关系会补充 `source_cases` 与 `source_batches`

## 13. 系统架构要求

- 采用前后端分离架构

## 19. 风险与注意事项

- 三列表 CSV 对格式要求严格，`名称(类型)` 不合法会直接失败
- 由于节点和关系 ID 按来源和来源医案分作用域生成，不同医案的同名实体会并存，这是当前设计选择，不是 bug
- 版本管理和审计日志目前不是完整生产级闭环，答辩或验收时必须明确说明
- 医家比较强依赖真实 Neo4j 数据和 GDS 插件，演示模式下不能把该功能当作已落地分析结果
- 路径查询当前输入的是实体 ID，不是自然语言关键词，使用时需要配合检索页先定位实体

## 20. 结论

当前系统已经形成“账号体系 + 图谱浏览检索 + 图谱管理 + 三列表导入 + 医家比较分析”的完整一期框架。后续补全重点不在重写底层，而在把版本发布、回滚、审计持久化和导入任务化这些治理能力补齐，形成真正可交付的生产版知识图谱管理系统。
